## rc.2 修了什么（相对 rc.1：test-only 修复）

- **根因是测试假设错误，不是产品缺陷**：原「maps read failures to BOARD_IO_ERROR」用例先
  `boot()`（`start()` + `update()`，此时 store 已有内存 snapshot 且 watcher 已安装），再注入
  `stat` 的 `EACCES` 并期望 `read()` reject。但 started store 的 watcher 会并发触发 reload；
  等待 in-flight reload 的 `read()` 可以合法地直接从缓存回答而不再调用 `stat`。该时序在较慢的
  CI 文件系统上出现时，读取 resolve 成 `{ revision: 1, … }` 而不是 reject。
- **修复（`board-io.spec.ts`）**：read-failure 用例改为在**从未 `start()` 的新 store** 上执行
  （无 snapshot、无 watcher、无 pending reload，`summary()` 为空），首次读取必然经过
  `stat`；另补一个注入 `readFile` 错误的同型用例。两者都确定性命中文件系统依赖 seam，
  与 watcher/缓存时序无关，断言 `BOARD_IO_ERROR`。
- **修复（`board.spec.ts`）**：原「read-only parent」用例依赖真实 `chmod(parent, 0o500)` +
  非 root uid 让 writer-lock 创建失败，并带 `skipIf(geteuid===0)`。现改为在
  `@deepseek-ai/dsh-atomic-write` 的 `withFileLock` seam 注入 `EACCES`（其余调用原样透传到真实
  实现），仍断言 `BOARD_IO_ERROR` 且看板字节不变；不再受 uid/umask/平台权限语义影响。
- **产品代码零改动**：`packages/*/src` 相对 rc.1 release commit `5d1cd7c` 无任何差异；
  变更只有两个 test-only 测试文件 + 版本 bump + 发布文档。
- **rc.1 的失败证据**（真实 CI）：rc.1 的 main push `verify` 失败，run
  [45159772716](https://github.com/yankeguo/dsh-devlead/actions/runs/45159772716)：
  `packages/devlead/tests/board-io.spec.ts > DevLeadBoardStore I/O error surface > maps read
  failures to BOARD_IO_ERROR`，`AssertionError: promise resolved "{ revision: 1, …(2) }" instead
  of rejecting`；同一 flake 也命中此前两次 main push（run `45154903696`、`45149005029`），而本地
  冻结树与同一 commit 的 tag publish run 均通过——属于时序相关 flake。rc.2 的 release commit
  以 main `verify` 全绿为 tag 前门禁。
- **rc.1 作废**：rc.1 的 tag/commit 保留为历史，但该候选不作为发布候选；其 6 条 staged npm 记录
  不得 approve（见文首提示）。

## 自 0.4.1 以来的内容（与 rc.1 相同）

汇总 `0.4.1..f69bd21` 的 5 个 commit（`e4ff951`、`4398e3d`、`fab1988`、`363a311`、`81140bc`）
+ rc.1 发布准备中的 P2/P3 收口。核心工具名/必填参数、`engines.dsh` 与 DSH 兼容面保持不变；
rc.2 只追加上述两处 test-only 确定性修复，不新增任何功能内容。

### 项目看板默认启用并跟随 active lead

- **零配置默认启用**：Host 在唯一的 active lead Session 上派生看板路径
  `<SessionHeader.cwd>/.dsh/devlead/board.json`。`SessionHeader.cwd` 是 Session **创建时的原始
  workspace 根**，不是某次 turn 的 worktree/effective cwd；worktree 隔离的 lead 仍把看板放在项目根。
- **单活即单 store**：同一时刻最多一个看板 store 与一个目录 watcher；`/devlead off`、lead 切换或
  workspace 根变化时先释放旧 store/watcher 再换到新路径；路径未变时复用同一个 store，读取不会看到
  半切换状态。
- **没有 lead / 没有绝对 workspace 根 → 看板禁用**：工具返回 `BOARD_DISABLED`、动态摘要为空、
  不注入浏览器 global、UI 不显示入口；不会伪造相对路径或回退到插件安装目录。
- **冷 workspace 缺失不再被重建**（rc.1 的 P2 收口）：派生路径（无 override）在 `start()` 前要求
  lead 记录的原始 workspace 根**仍是已存在目录**。该目录被删除/移走/变成普通文件时，看板以新
  reason `missing-workspace` 保持 disabled（`ctx.devLead.boardDisabledReason` 可读），记录一条
  warning，**不会 `mkdir` 重建 workspace 根、不会写入任何文件**，工具返回 `BOARD_DISABLED`。
  workspace 恢复后，下一次 lead 同步/切换重新解析并启用；显式 `boardPath` override 保持既有
  预创建语义（见下）。
- **start 失败只降级**：父目录预创建 / `start()` 失败只记录 warning 与 `boardStartError`，
  DevLead 服务、工具、命令与 UI 照常加载；board 工具随后按真实故障返回 `BOARD_IO_ERROR`、
  摘要保持空。同一 resolved 路径的下一次 lead 同步也会**按需重试** `start()`（rc.1 的 P3 收口），
  路径切换则天然重新启动；重试仍失败时保留最后一次真实故障。

### 浏览器：lead-only 只读看板

- `dsh.client.inject` 仍是静态声明；right-Sidebar 的看板 tab type、guide entry、keyed body、
  动态标题与会话头按钮只在**屏幕上的 eligible lead**（top-level Session 且 summary 的
  `devLeadMode` 为 enabled；subagent 永不合格）出现，模式关闭/切换 Session 立即注销并关闭当前
  Session 遗留的看板 tab（rc.1 的 P3 收口：**页面恢复出来但已非合规 lead 的 tab 在首次 sync 也会被
  关闭**，即使本页从未注册过看板 surface）。
- Host global `__DSH_DEVLEAD_BOARD__` 新增 additive 字段 `leadSessionId` 与 `override`；
  global 缺失时 client 从 lead Session summary 的 `cwd` 自愈派生默认路径，因此**默认路径部署的
  late-enable 不需要刷新页面**。使用 Config `boardPath` override 的部署在页面先于 lead 加载的
  场景仍需刷新一次页面才能拿到 override 路径（已知限制，见下）。
- 面板**直接读取看板文件**（schema 的 256 KiB 文件上限；模型工具的 64 KiB 读取裁剪不作用于面板），
  严格复用 protocol 的同一份 schema v1 解码；文件尚不存在时按有界退避轮询（4s 起、上限 30s）等待
  首次写入，watch 断开时明确提示手动刷新，区分「还没有看板数据」与读取/解析失败。

### 工具：64 KiB 读取上限与长引用修复

- `devlead_board_read` 的结果序列化上限为 `DEVLEAD_BOARD_READ_MAX_BYTES = 64 KiB`（Host 与浏览器
  共用 protocol 常量）。超限时按固定顺序**从尾部整行裁剪** tasks → blockers → whole project 行，
  保留 revision/updatedAt 与靠前内容，并标 `truncated:true`；不会返回 schema-invalid 的行片段。
- `devlead_board_update` 的 project 引用（id / workspace title / 绝对 workspace path）在锁内
  fresh snapshot 上解析；写入预检使用固定 synthetic id，因此**长 workspace path/title 不再误报
  `BOARD_LIMIT_EXCEEDED`**，未知引用仍为 `BOARD_PROJECT_NOT_FOUND`、title 歧义仍为
  `BOARD_PROJECT_AMBIGUOUS`。
- 稳定错误码新增/使用：`BOARD_DISABLED`、`BOARD_NOT_FOUND`、`BOARD_INVALID`、
  `BOARD_PROJECT_NOT_FOUND`、`BOARD_PROJECT_AMBIGUOUS`、`BOARD_REVISION_CONFLICT`、
  `BOARD_LIMIT_EXCEEDED`、`BOARD_IO_ERROR`。工具从不接受看板文件路径参数。

### boardPath override 兼容语义

既有显式 `boardPath` 部署升级后**路径、权限与 CAS 语义都不变**：仍必须是绝对路径（相对路径直接
拒绝，不按 cwd resolve），仍优先于 active lead workspace 派生，仍在 `start()` 时以 `0700`
幂等预创建父目录（不修改已有目录权限），写入仍是同目录临时文件原子替换 + `withFileLock` 跨进程锁；
文件权限 `0600`。override 路径不受 `missing-workspace` 限制（不依赖 lead workspace 存在）。
路径最终组件不能是 symlink（原子替换会替换链接本身）；目录链中的 symlink 可正常工作。

### 包拓扑修正

`@yankeguo/dsh-client-ui-devlead` 现在只依赖 `@yankeguo/dsh-devlead-protocol`（从 protocol 读取
`DEVLEAD_BOARD_SCHEMA_VERSION`），**不再依赖 `@yankeguo/dsh-devlead`**：浏览器包与 Host 核心包
解耦，安装图与发布拓扑保持一致（protocol → {client-ui, devlead} → … → bundle）。

## 已知限制

- **`boardPath` override + 页面早于 lead 加载**：late-enable 场景需要刷新一次页面才能拿到
  override 路径与 `override:true`（默认派生路径不需要刷新）。
- **没有 active lead、没有绝对 workspace 根、或派生 workspace 根缺失** → 看板禁用
  （`BOARD_DISABLED`；`boardDisabledReason` 分别为 `no-workspace` / `missing-workspace` 等）。
  Host 不重建缺失的 workspace，也不会迁移旧 lead 的看板文件。
- **start 失败** → 看板 degraded（`BOARD_IO_ERROR`，摘要空），其余 DevLead 功能不受影响；
  修复文件系统问题后等待下一次 lead 同步/切换或重启即可重试。
- 浏览器在 lead 的 workspace 根缺失时仍可能按 summary `cwd` 自愈出一个只读入口，显示空态/
  读取错误；浏览器只做 `stat`/`readBytes`，绝不会创建目录或写入。
- `.dsh/devlead/` 是否加入仓库 `.gitignore` 由用户/仓库所有者决定；插件不修改 `.gitignore`，
  也不要求看板进入 Git。
- 浏览器视觉/主题/交互仍需按 [UI-VERIFICATION](../UI-VERIFICATION.md) 在隔离 profile 人工验收；
  自动化覆盖到 projection/DOM/断言层，不替代人工走查。

## English summary

v0.4.2-rc.2 is the second prerelease candidate for the planned 0.4.2 patch release and supersedes
the never-approved 0.4.2-rc.1. It carries the same feature set as rc.1 — the project board is
**enabled by default** for the active lead, derives its file from that Session's original workspace
root (`<cwd>/.dsh/devlead/board.json`), follows the single active lead without churn, and exposes a
**lead-only read-only right-Sidebar UI**; an explicit deployment `boardPath` keeps its existing
absolute-path, pre-create and CAS semantics; the tool-facing board read is capped at 64 KiB
(tail-trimmed, `truncated:true`); long workspace-path/title project references no longer false-fail
with `BOARD_LIMIT_EXCEEDED`; a board start failure only degrades the board (`BOARD_IO_ERROR`); a
derived board requires the recorded workspace root to still exist and is **never recreated** when the
workspace disappears (`missing-workspace`); and the client-ui package no longer depends on the core
package. The changes in rc.2 are **test-only determinism fixes**: the board read-failure test now
injects the filesystem error into a fresh, never-started store instead of relying on watcher/cache
timing (the CI flake), and the writer-lock permission test injects an errno at the `withFileLock`
seam instead of using real `chmod`/non-root uid. There are **no product code changes** versus rc.1,
no public API breaks, and the DSH compatibility surface (`0.2.2-rc.1` – `0.2.2-rc.5`) is unchanged.
The 0.4.2-rc.1 staged npm records were never approved and must not be approved; rc.1's main `verify`
was red on that flake. Nothing is public until a maintainer approves the staged rc.2 versions on
npmjs.com; the release uses npm dist-tag `next` and leaves `latest` at 0.4.1.
