# v0.2.1 — staged 发布流水线与插件展示元数据

0.2.1 是 **patch 版本**，DevLead 的运行时行为不变：本版把发布流程改为 **npm staged publish**
（CI 只 stage、维护者人工 approve 后才公开），并为全部 6 个可发布包补齐 DSH 插件管理器 / 插件
市场使用的用户友好展示元数据（中英双语）。持久记录格式、公开 API、`engines.dsh` 均不变。

## 发布模型：CI 只 stage，人工 approve，再出 GitHub Release

旧的「CI 直接 `pnpm publish -r` + CI 创建 GitHub Release」模型已废弃。新流程见
[发布指南](../PUBLISHING.md)：

1. **Stage（CI）**：推 `v*` tag（或 `workflow_dispatch` 传入已存在的 `release_tag` 重跑）
   触发 [`publish.yml`](../../.github/workflows/publish.yml)。工作流先校验 tag commit == HEAD、
   tag 版本与根 + 6 个包完全一致（prerelease tag 直接拒绝），再 install / typecheck / test /
   build / `check-packages`，最后按 workspace 依赖拓扑顺序对每个包执行 `npm stage publish`。
   **此时不会公开任何版本**；CI 通过 OIDC 短时 token（`id-token: write`）逐包换取权限，
   provenance 在公开仓库自动附带，不需要任何 `NPM_TOKEN` secret。
2. **Approve（维护者本机）**：`npm login` + 交互式 2FA 后运行
   `node scripts/promote-release.mjs --version 0.2.1`（可先 `--list-only` / `--dry-run` 查看）。
   脚本先做只读预检（每包恰好 1 条 staged 记录、npm/gh 登录、远端 tag、release notes），
   全部通过后才逐包 `npm stage approve`；失败时打印已公开包、剩余 stage id 与 `reject` 清理提示。
3. **Release**：全部批准后由同一脚本幂等创建/更新 GitHub Release（`--verify-tag`，
   notes 取自 `docs/releases/v0.2.1.md`）。

新增/变更的发布工具：

- `scripts/stage-release.mjs`（新）：`pnpm pack`（改写 `workspace:*` 为精确版本）→ 断言 tarball
  manifest → `npm stage publish`；确定性拓扑顺序（protocol → client-ui → devlead → command →
  tool → bundle）、首个失败即停、job summary 输出 stage 表、临时目录自动清理；
  `--dry-run` 用 `--force` 跳过 registry「版本已存在」检查，供本地预检。
- `scripts/promote-release.mjs`（新）：两阶段（只读预检 → 串行 approve），OTP 交互、
  已发布幂等跳过、duplicate/missing 明确报错、失败恢复提示、幂等 GitHub Release。
- `scripts/trusted-publishers.sh`：改授 `--allow-stage-publish`（不再 `--allow-publish`）；
  旧 publish-only trust 配置需 `npm trust revoke` 后由脚本重建。
- `publish.yml`：`workflow_dispatch` 新增 `release_tag` 输入（checkout 既有 tag，
  不创建/移动/删除 tag），移除 CI 内 GitHub Release 与 `contents: write`。
- npm CLI：staged publishing 自 npm 11.15.0 提供，CI 固定并验证 **11.20.0**。
- `scripts/check-packages.mjs`：新增 staged-publish 契约检查（禁止 CI 直发 / CI 建 Release /
  裸 `npm publish`，要求 stage 脚本、`release_tag` 输入、`--allow-stage-publish`、根 scripts 映射）。

## 插件展示元数据（`locale/en.json` + `locale/zh.json`）

DSH 0.2.2-rc.1 插件管理器/插件市场通过 `readPluginMeta` 读取
`<包名>/locale/en.json` 中的 `{"meta":{"title","description"}}`，同目录其它语言文件作为翻译，
字段缺失才回落到包名 / `package.json` description。本版 6 个包全部补齐（title 中英各一）：

| 包 | English | 中文 |
| --- | --- | --- |
| `@yankeguo/dsh-devlead-protocol` | DevLead Protocol | DevLead 协议 |
| `@yankeguo/dsh-devlead` | DevLead | DevLead |
| `@yankeguo/dsh-tool-devlead` | DevLead Tools | DevLead 工具 |
| `@yankeguo/dsh-command-devlead` | DevLead Command | DevLead 命令 |
| `@yankeguo/dsh-client-ui-devlead` | DevLead UI | DevLead 界面 |
| `@yankeguo/dsh-devlead-bundle` | DevLead Suite | DevLead 套件 |

- 每个包 `package.json` 增加 `files: ["locale/*.json"]` 与
  `exports: { "./locale/*.json": "./locale/*.json" }`；bundle 保留 `icon.svg`；
- `client-ui` 既有两个 locale 文件的标题由「DevLead mode/模式」更新为「DevLead UI/界面」，
  并同步 `src/client/locales.ts` 的 `meta.*`（既有 `locales.spec.ts` 保证一致）；
- 新增 `packages/devlead/tests/plugin-metadata.spec.ts`：校验 locale 存在/合法、en+zh 字段
  非空、`files`/`exports` 接线、标题唯一、无营销最高级词，并通过 Node `exports` 真实解析
  `<pkg>/locale/{en,zh}.json`（与 DSH 解析路径一致）；
- `scripts/check-packages.mjs` 增加同样的 CI 静态校验，新增包漏配 locale 会在发布前失败。

## 验证

```sh
pnpm verify                      # typecheck + tests + build
node scripts/check-packages.mjs  # OK (6 packages)
node scripts/stage-release.mjs --dry-run   # 6/6 打包 + npm 预检，不上传
node scripts/e2e-smoke.mjs --flow patch --no-worktree --no-build      # 39/39
node scripts/e2e-smoke.mjs --flow installed --no-worktree --no-build  # 39/39
```

- `pnpm verify`：typecheck 通过；**23 文件 / 580 tests passed**；build 6 targets。
- `node scripts/check-packages.mjs`：OK (6 packages)（含新增 locale / staged-publish 规则）。
- `stage-release --dry-run`：6 个包按拓扑顺序打包，逐个通过 npm 11.20.0 的 dry-run 预检。
- E2E 冒烟：`patch` 与 `installed` 两条加载流各 **39/39**（阶段 1 = 27 + 阶段 1b = 12；
  `--no-worktree` 跳过需实验 forge bundle 的阶段 2）。
- 版本：根 `package.json` 与 6 个可发布包统一为 `0.2.1`，`check-packages` 校验版本锁步。
