## Lead-only board workflow

新增独立 system prompt section **`devlead:board-policy`**，正文为 `DEVLEAD_BOARD_POLICY`（785 chars），
仅在 `ctx.devLead.isEnabled(agent)` 时解析为可见文本；普通 Session 与无 Agent 的 prompt assembly 均为空。
独立 section 不扩充 `DEVLEAD_POLICY_BASE`，保留其原有 +10% 尺寸预算；新 section 另有 400–800 chars 测试预算。

引导把每轮注入的 board summary 作为跨项目状态事实源，并要求：

- 派发/收口，或项目 focus、next、blockers、tasks 有实质变化时，用 `devlead_board_update` 批量合并更新；
- 计划、设计、决策、交接等值得跨轮保留的内容写入 `devlead_board_note_write`；恢复项目或写派发简报前，
  先用 `devlead_board_note_read` 读取既有 notes；
- 向用户汇报前先把过期看板状态对齐现实；保持内容简短可读，不整段复制聊天、日志或工具输出；
- `BOARD_DISABLED` / `BOARD_IO_ERROR` 时继续主任务，只报告一次降级，不反复重试；没有实质变化时不制造
  无意义更新或播报。

board disabled 时的空摘要与既有错误语义不变。

## 四个工具的使用场景描述

四个既有 description 保留全部原有参数、路径、有界读取与 CAS 约束，各补一句 `Use when …`：

- `devlead_board_read`：派发、恢复、收口或汇报前核对当前跨项目状态；
- `devlead_board_update`：派发/收口或 focus/next/blockers/tasks 实质变化时批量更新；
- `devlead_board_note_read`：恢复项目或准备派发简报时读取既有计划、决策与交接；
- `devlead_board_note_write`：需要跨轮保留计划、设计、决策或交接时写简短 note，而非复制 transcript/log。

实际 description 定义位于 `packages/tool/src/board-tools.ts`；`parameters.ts` 的参数 schema 未改变。

## 发布方式：stage → 人工 approve → GitHub Release

1. 人类明确批准后，推送指向最终 release commit 的 annotated tag `v0.4.2-rc.6`。CI 使用 OIDC trusted
   publishing，以 npm **`next`** dist-tag **stage** 全部 6 个包并生成 provenance；**stage 不公开任何内容**。
2. 维护者在 npmjs.com 网页核对本次 CI 的 6 条 staged 记录：版本必须全部为 `0.4.2-rc.6`、dist-tag 必须为
   `next`，然后人工批量 approve。approve 即公开且不可撤销；approve 后 `next` 指向本候选，`latest` 仍为
   **0.4.1**。不要批准 rc.1 或 rc.4 的未 approve 历史 staged 记录。
3. approve 完成并核对 dist-tags 后，使用既有 tag 和本文件手动创建 prerelease GitHub Release：

   ```sh
   gh release create v0.4.2-rc.6 --repo yankeguo/dsh-devlead --title v0.4.2-rc.6 \
     --notes-file docs/releases/v0.4.2-rc.6.md --verify-tag --prerelease --latest=false
   ```

4. 最后做三方核对：6 个包的 `@0.4.2-rc.6` 在 npm 可见、`dist-tags.next = 0.4.2-rc.6`、
   `dist-tags.latest = 0.4.1`；GitHub Release 指向 tag `v0.4.2-rc.6` 与同一 commit，
   `isPrerelease=true`、`isLatest=false`、`isDraft=false`。

## English summary

v0.4.2-rc.6 builds on the published rc.5 candidate with model-facing guidance only. A new independent
`devlead:board-policy` section is visible exclusively to an enabled lead and stays within a 400–800-character budget,
leaving the resident base policy unchanged. It makes the per-turn board summary the cross-project source of truth,
asks for batched updates at dispatch/close and material state changes, notes reads before project resumption or
dispatch briefs, concise durable plans/decisions/handoffs, stale-state reconciliation before reporting, one-time
degradation reporting, and no noisy no-op writes. The four existing board/notes tool descriptions gain concrete
`Use when …` scenarios without losing their constraints. Schemas, tool semantics, UI, Host APIs and DSH compatibility
remain unchanged. Stage publishes nothing: maintainers must approve only the six new rc.6 `next` records before
creating the prerelease GitHub Release; `latest` stays 0.4.1.
