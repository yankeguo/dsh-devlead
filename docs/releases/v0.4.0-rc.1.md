### 主线一：In-Turn / Question 消息传递（Phase 1d/1e lanes）

- **三条投递 lane**落地：`turn-notice`（completed/forked 走 `followup`，保留 400ms 合并）、
  `action-required`（blocked/decision/review/question 走 `steer`，只表示立即调度 flush，
  最早在下一个 pre-step 被 claim）、`background`（progress/fyi 走 `inject`，不请求 driver
  wake）。模型不暴露 `queue|steer|inject` 枚举，runtime 按类别与目标状态选 primitive。
- **answer / correction steering**：`devlead_prompt_session` 的 `intent`
  （`instruction|answer|correction|background`）、`question_id`、`idempotency_key` 与
  `devlead_report` 的 `kind` 共同决定 lane；answer/correction 走 steer 优先道（running/idle
  均 steer，cold 先 resume；`interrupt:true` 仍覆盖为 cancel + followup）。
- **conversation 三 lane 的读侧**：`devlead_notifications` / `devlead_get_session` 输出
  通知行的 `wakeSuppressedByReportId` / `wakeSuppressionReason`，report 行的诊断 `lane` 与
  内存 `deliveryState`，`queuedInputs` 的 `intent` / `questionId` / `wakeRequested` /
  `deliveryState`；question report 行附带 fold 派生的 `questionStatus` / `answerStatus` /
  `answerMessageId` / `answeredAt` / `presentedAt`。runtime 侧新增
  `DevLeadProjectionReport.repairPending`（whole-value `plugin:devlead/repair` 记录驱动，
  mark/clear 双向发布），DevLeadBar 在 question 生命周期后显示 `provisional` /「暂定」。
- **lane UI**：DevLeadBar 按 lane 着色（turn-notice / action-required / background），
  question 状态与 wake 提示进入状态条文案；三类 header 语义
  （`[DEV LEAD NOTIFICATION]` / `[DEV LEAD ACTION REQUIRED]` / `[DEV LEAD REVIEW REQUIRED]`）
  与 policy 文案对齐。
- **背压与指标**：action-required 16/pair 共享上限（Q1/P3/P4），background 8/lead-turn +
  16/pair 预算降级为 digest-only；correction/background 每 child-turn 4/8 上限返回
  `DEVLEAD_DELIVERY_RATE_LIMITED`；新增 `actionRequiredBatchMs`（0–400ms，默认 0）配置。
  `DevLeadMetrics` 低基数计数器（delivery / suppression / guard / answer / question）由
  `service.metricsSnapshot()` 暴露，供发布前评估 turn-boundary 收益。

### 主线二：cold-discard durable / repair 收口与 cold supervision 加固

- **OUTBOX spec v3**：`devlead_report_outbox` 升级为 v3、**无 compatible versions**，
  pending report 的 `origin:'live'|'cold'` 必填；旧 v1/v2 domain、无 origin 行与旧
  answer-discard 队列数据显式丢弃。旧 domain 打不开时 warn 并禁用该 durable domain，
  不 crash、不写入。`answer_discards` 单独保留 **30 天** retention。
- **answerSeq / cold-origin replay**：per-question admission 序号确定 latest answer（延迟旧
  discard 不压新 re-answer）；cold-observed background 经 outbox/persistReport replay 或
  跨重启只 append receipt + digest-only，绝不 inject；`coldQueuedReports` marker 在
  settle/drop/dedupe/degrade/watch 变化时清除，live 后也不误投。
- **repair barrier / repairPending**：prompt 在 question policy guard 前等待 drain/repair
  barrier（`REPAIR_BARRIER_TIMEOUT_MS` 30s + `ANSWER_DISCARD_DRAIN_TIMEOUT_MS` 30s，
  abort 安全退出、可重试）；无法证明 survival 时 view 保持 `repairPending`、prompt 以
  `DEVLEAD_SESSION_UNAVAILABLE` fail closed，不静默接受重复 answer；in-flight drain 窗口
  （`drainingAnswerDiscards`）对 view/health/prompt 一致可见。
- **multi-batch cold supervision rehydration**：持久语料扫描按 64 读批次、12 次尝试上限 +
  30s 慢速探针；finalize 复核/append 批次各自独立 5s 窗口（单次 attempt 理论最坏约 30s）；
  `unverifiable`（读不出持久真值）保留 trusted 快照/游标/高水位并计失败，只有可读的不一致
  （`changed`）才丢弃重扫；corpus 授权绑定到真实 service provision 身份，admission 入口、
  drain/repair 之后与真正同步投递前各复核一次，`ctx.set` 原地替换/移除期间 fail closed；
  plugin dispose 通过服务生命周期 abort 取消进行中的验证读取。

### 主线三：A 加固（plugin-record 依赖与隐私）

- **plugin-record API 探测 / 降级**：`record-api.ts` 在 init 探测 `appendPluginRecord` /
  `pluginRecordOf` 两个导出，首次读/写异常转入 `degraded`；失败的那次 append 返回 `false`
  而非抛出、read 返回 `undefined`，只 warn 一次。degraded 时 fold 保持最后有效状态
  （不写 `failure`、不冻结），`/devlead status` 与每个成功命令视图明示 memory-only。
- **隐私披露**：plugin records 是 canonical session-log events，会进入 session-log ZIP
  导出；DSH 默认组合、默认 `enabled: true` 的 `session-log-deepseek` 可能把完整 canonical
  event 附加到符合条件的官方 DeepSeek 模型请求。README / COMPATIBILITY 记录该上传路径与
  关闭方式；DevLead 不新增上传、不改 DSH 默认配置。
- **升级门禁**：COMPATIBILITY 重写为可执行门禁——核对 record API 声明与语义、deprecated
  reader 清零、逐 rc 临时 typings 编译 + 真实 E2E recipe、record schema/migration 核对。
- **`Session.snapshotEvents()` 迁移完成**：生产调用 **0**（`snapshotEvents()` /
  `eventAt()` / `ownEvents()` 均无调用）。inbox 入队时间、turn source 与 child answer
  survival 改由有界 Session projection 承载，cold 侧以 `observeSession()` 读 projection
  wire value，不再把同步全日志扫描改成异步全日志扫描。rc.1 没有 `inspectSession()`，因此
  child-answer projection 带 `wire.summary:false` 以同时支持 rc.1 与 rc.5。
- **F 替代方案 no-go 结论**：从 DSH 核心事件派生 mode/watch/reset 的一次性 spike 判定
  no-go（6 个实质反例），plugin records 的 experimental 依赖仍在；缓解路径是上述 A 加固 +
  升级门禁。结论与重估条件见 [DESIGN](../DESIGN.md) §4.4.12。

## Breaking changes

0.4.0-rc.1 按「正确性 > 兼容性」执行，以下变更是**有意的**、不提供自动迁移：

- **旧 DevLead 状态丢弃**：7 类 `plugin:devlead/*` record 统一为 `version:2`；v1 record 与
  无 `answerSeq` 的 answer 显式忽略并丢弃（每进程一次 warning），**不冻结** projection。
  升级后旧 Session 的 DevLead 模式/关注集/digest/answer 状态失效，需要重新 `/devlead on`
  并按需重建关注。
- **当前版本损坏仍冻结**：当前 v2 payload 的字段/类型损坏仍设置 `failure` 冻结 projection，
  `/devlead reset` 恢复；坏 reset 不能解冻。
- **projection stateVersion**：`devLead` 7、`devLeadMode` 3、`devLeadWatch` 3；旧缓存行整体
  失效并从 durable log 重新 fold。
- **outbox v3 无兼容**：`OUTBOX_SPEC` v3 无 `compatibleVersions`，`origin` 必填；旧 v1/v2
  outbox、无 origin pending row、旧 answer-discard 队列数据全部丢弃；旧 domain 无法打开时
  禁用该 durable domain。`answer_discards` 30 天 retention 不变。
- **answerSeq 必填**：answer 生命周期事实必须携带 per-question 序号，缺少序号的旧 answer
  record 被忽略（不能作为 answered/presented 证据）。
- **multi-lead 硬门禁**：prompt 侧 foreign / multiple supervisor 直接拒绝
  （`DEVLEAD_FOREIGN_SUPERVISOR` / `DEVLEAD_MULTIPLE_SUPERVISORS`），在任何 watch/resume/
  admission 副作用之前；supervisor 集合不可证明（无 cache、capped unknown、stale-negative、
  读取失败）时以 `DEVLEAD_SESSION_UNAVAILABLE` fail closed。
- **question TTL 默认 24h**：`questionTtlMs` 默认 `86400000`，`0` 禁用；只让当前仍 open 的
  question lazy 过期，answered 不 retroactive 过期；过期 answer 返回
  `DEVLEAD_QUESTION_NOT_FOUND`。cold 恢复对 durable、open、未过期 question 每进程最多
  replay 一次，与普通 action report 共用 16/pair 容量。
- **非 answer 幂等改为 durable**：receipt 持久在独立 `devlead_idempotency` v1 domain 的
  `receipts` 表（textHash/delivery/at，7 天 TTL + 启动清理）；同 key 同文本返回原 receipt，
  不同文本冲突。receipt read 的 absent 与 unreadable/corrupt 严格分离，后者以及 composed
  storage 打不开时在 admission 前 fail closed；只有 Host 未组合 storageDomain 时才显式
  warning 后走进程内窗口。
- **旧 Session 相关状态需 reset**：升级后受影响的 DevLead Session 用人类命令
  `/devlead reset`（或冻结折叠时的 `/devlead off`）恢复；reset 是唯一在冻结检查之前应用的
  record。
- **UI / 配置面**：三 lane header、lane 着色、question 状态与 `provisional` 标记为新增
  UI 行为；`actionRequiredBatchMs`、`questionTtlMs`、`DevLeadProjectionReport.repairPending`
  为本版新增的配置/投影字段。

## 升级注意事项

- **旧 devlead 状态不迁移**：不要期望升级后旧 Session 保留模式、关注集、通知 digest 或
  answer 状态。受影响的 Session 打开后运行 `/devlead reset`（reset 需要 live Agent；
  冷 Session 先 resume/open）。
- **回滚也会丢状态**：回滚到 0.3.0-rc.2 或更旧版本时，旧 fold 对已知类型的 v2 payload 会
  freeze，需要 `/devlead reset`；不能宣称“回滚不会因新记录损坏日志”。
- **配置**：`questionTtlMs`（默认 86400000，0 禁用）与 `actionRequiredBatchMs`
  （0–400ms，默认 0）在 loader row `devlead` 的 `config` 覆盖；不要用 deployment 默认值
  推断运行行为。
- **multi-lead 硬门禁**：Host 级仍只允许一个 active lead；第二个 lead 必须先
  `/devlead off`。archived holder 不阻塞新 enable。
- **引擎/兼容面不变**：`engines.dsh: >=0.2.2-rc.1 <0.3.0` 与全部 `@deepseek-ai/dsh-*`
  peer 范围不变，devDependencies 仍固定 rc.1 做最旧 API 类型检查；本版不声明 DSH 0.4。
- **record API 仍为实验性扩展点**：升级 DSH 前必须按 [COMPATIBILITY](../COMPATIBILITY.md)
  的升级门禁重跑（record API 探测/降级、deprecated reader 清零、逐 rc recipe、真实 E2E）。
- **发布顺序**：6 个包同版本、依赖先发布、bundle 最后；不要只升级部分包。

## 已知限制与 follow-up

- **慢但可读（2–5s）的持久 listing 可能 fail-closed 到 cap/30s probe（可用性加固项）**：持久
  语料 listing 慢但可用时，就绪 barrier 会超 2s 界（`REHYDRATION_READINESS_TIMEOUT_MS`）并返回
  unverifiable；入口 verify 即使成功仍可能无法 finalize——finalize 复核使用独立的 5s 预算
  （`REHYDRATION_FINALIZE_TIMEOUT_MS`），需覆盖同一 attempt 内两次 2–5s 读取。因此后端保持该
  延迟时，rehydration 会保留 trusted 快照/游标/高水位并计入失败预算，12 次失败后进入 sticky
  cap + 30s 慢速探针，恢复前 prompt 保持 fail closed（`DEVLEAD_SESSION_UNAVAILABLE`）。这是
  安全方向（期间不授权），**不是数据损坏**：原因消除后 probe 从保留游标 finalize，不重读已扫
  行。根因是 round-7 FINAL SAFE 的 **M1**（medium，barrier unverifiable 后仍以
  `listing !== undefined` 作为 finalize 前置）；GA 前 follow-up：改用 effective
  validatedListing（barrier listing 或入口 verify ok），或在入口 verify 成功后允许 finalize，
  并补 2s<L<5s 慢 listing 恢复测试。
- **delivery-time supervisor 集合的窄 TOCTOU 窗口（medium，未复现）**：delivery-time
  `SupervisionProof` 只含 `{ bindings, corpusBacked }`
  （`packages/devlead/src/index.ts:393-399`），只绑定 corpus service 身份与 rehydrated 状态；
  supervisor/watch 冲突只在 gate 时计算一次（`hub.supervisorsOf`，`:4138` 附近）。admission 内
  drain/repair/resume/interrupt 等 await 期间若 supervisor/watch 集合变化，delivery 复核
  （`assertSupervisionProofHeld`，`:4166-4175`；调用点 drain/repair 之后 `:3608`、`admitPrompt`
  入口 `:5766`、真正 `followup/steer/inject` 之前 `:5888`）只重查 corpus
  bindings/rehydrated，**不重算 supervisor/watch 集合**。因此存在窄、未复现的 fail-open 窗口
  （medium）：单 active lead 架构下需要并发 watch 变更（另一 lead 的 watch/冷恢复）才可能触发，
  本轮未构造出单进程可达路径；若未来把投递改成异步/分批，窗口会扩大。GA 前建议把 sorted
  watcher ids（含 archived 输入）纳入 proof 并在 delivery 前重跑冲突判定，补“resume 期间
  foreign watch 出现”负控（可选 follow-up，复核原文见 [DESIGN](../DESIGN.md) §12）。
- **`repairPending` 不是 answer 的 durable 完成证明**：它是 runtime repair 集合的
  whole-value 投影，answer admission 仍以 runtime repair barrier 为准；presented 证据被
  evict 后对应 question 的 stale discard repair 可能长期保持 unknown（per-question），直到
  pending/claimed/presented 等新证据出现。
- **round-7 FINAL SAFE 的 4 项 low 代码 nit（已接受，本 RC 不改代码）**：① `proof ===
  undefined` 时 delivery 复核直接放行；`createSession` 的新 Session admission 本就不需要 gate
  proof，当前不可利用，但类型上允许未来调用方静默跳过（建议改成必填或显式 sentinel）。② probe
  reset 清 `rehydrationValidationTimedOut` / `FinalizeBlocked` 但未清
  `rehydrationValidationUnverifiable`（当前由 attempt 入口/finally 兜底，属 parity 缺口）。
  ③ `rehydrationScanHighWater = nextIndex` 而非 `Math.max(old, nextIndex)`：记录重排/同集合
  resume 时可能调低高水位，弱化“越过上次失败点”的约束（未构造触发）。④ scan-entry 的 `changed`
  保留快照/游标，而 finalize 复核与 not-found 两处 `changed` 丢弃，与“只有 `changed` 丢弃”的
  文档表述不完全一致（pre-existing）。四项均为低风险加固项，列入 GA 前 follow-up，详见
  [DESIGN §12](../DESIGN.md)。
- **浏览器视觉验收是人工 checklist**：lane 着色、question 状态、`provisional` 标记与状态条
  布局不能只靠单测判断，按 [UI-VERIFICATION](../UI-VERIFICATION.md) 在隔离 profile 里人工
  验收；本 RC 的自动化证据只覆盖 projection/DOM/渲染断言。
- **`possibleQuestion`（自然语言提问启发式）明确不做**：本 RC 不实现、不加标记，理由是会
  把普通文本误判为 question 并改变 transport（打断/错误 lane），而当前 question gate 已覆盖
  真实 `ask_user_question` 路径；留作 backlog，仅在真实模型行为证明需要时重新评估。
- **blocking bridge 只记录指标评估结论**：本 RC **不实现** blocking bridge / wait tool，
  只保留 Phase 3 条件性计划（capability flag、插件内原型；不涉及 DSH 上游改动）；是否值得
  做由 `metricsSnapshot()` 的 turn-boundary/延迟指标决定，不作为本版发布承诺。
- **低优先级对齐/文档 nit**：双语 README 与 DESIGN/COMPATIBILITY 措辞对齐、证据索引与
  Phase 1d r7 证据的退出码说明已在 Batch 2 修正；本版另做两轮文档修复（release notes 与
  round-7 FINAL SAFE 的 known-limitations 一致性、范围账目、breaking 归属、UI 验收 checklist、
  日期与 `NOWORKTREE_EXIT`，以及发布前的 evidence 措辞/排版 polish）；`packages/` 除
  `packages/devlead/src/fold.ts` 一处 JSDoc 注释外未改，版本与构建产物不变、无运行时行为变化，
  修复后重跑门禁均通过。
- **3 条 e2e 检查为 SKIP**：本机 provider 的可用 model list 不含所请求的
  `deepseek-official/deepseek-flash`（无凭据/路由不可用），三条 e2e 各有 3 条正向模型选择
  检查 SKIP，SKIP 未执行、不能算通过。
