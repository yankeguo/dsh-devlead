## P2：跨平台 note id / path 身份

- 共享 protocol schema 在项目内按 `id.toLowerCase()` 判重、全局按 `path.toLowerCase()` 判重；`CaseNote` 与
  `casenote` 不再能在大小写不敏感文件系统上静默串正文。Host create 在写正文或 index 之前返回
  `BOARD_INVALID`，client 使用同一 decoder 自动拒绝。
- note id 与 project directory 拒绝 Windows 设备保留名 `CON/PRN/AUX/NUL/COM1-9/LPT1-9`，覆盖大小写、
  扩展名及尾随空格/点变体；普通 `COM10` 等名字不受影响。protocol、Host 和 client 都有 accept/reject 测试。

## P3：读取、client 生命周期与恢复

- **64 KiB 模型读取**：单 note 磁盘正文仍可达 256 KiB，但 `devlead_board_note_read` 的完整 JSON 结果现在
  不超过 64 KiB。过长 `content` 按 Unicode 码点边界保留前缀并返回 `truncated:true`；`note.bytes` 仍描述
  完整磁盘正文，浏览器 reader 仍读取完整文件，不用截断结果覆盖原文。
- **fatal UTF-8**：Host 的 index 与正文都改用 fatal `TextDecoder`，即使字节数与 metadata 相同，非法 UTF-8
  也返回 `BOARD_INVALID`，与 client 一致。
- **path 代际**：`useWorkspaceFile` 在新 path 首次读取完成前隐藏旧 `valuePath` 的 value；打开 reader 切换
  workspace 时不会闪现旧 chips、metadata 或正文。
- **减少冗余 I/O**：`useDevLeadNote` 以原始 `id/path/bytes` 和 notes root/platform 为 memo key。index poll
  只产生新 metadata 对象时不再重开 note watch 或重复 stat/readBytes，bytes 代际变化仍会刷新正文。
- **a11y**：视觉「正在刷新」与独立 polite live region 分离；每 5 秒轮询的 busy 翻转不再重复播报，健康/
  生命周期迁移和错误仍保留提示。
- **orphan/GC 与坏 index 恢复**：`docs/BOARD.md` 写明先停用 writer、备份，再修复/删除滞留 project entry
  或整个 notes 目录的步骤；也区分未索引 orphan、正文缺失的 stale metadata 与 board 重建后的上限占用。
- **真实 tool 面**：E2E 新增 `devlead_board_note_read` 经 `ctx.tools.resolve/execute` → 参数转换 →
  active-lead service → committed Markdown 的检查，不再只覆盖 direct service。phase 3 pin 由 140 增至 141。

- 从 rc.4 升级不需要 board/notes 数据迁移或 `/devlead reset`。共享 schema 会拒绝此前可能冲突的大小写
  metadata；如旧 index 已含冲突，先按 [BOARD 恢复说明](../BOARD.md#坏-indexorphan-与-board-重建后的恢复)

  **`0.2.2-rc.1` – `0.2.2-rc.5`**，`engines.dsh` 保持 **`>=0.2.2-rc.1 <0.3.0`**。实现不新增
  `dsh.client.inject`、Remote 或 0.2.3-only API。

## 发布方式：stage → 人工 approve → GitHub Release

1. 人类明确批准后，推送指向最终 release commit 的 annotated tag `v0.4.2-rc.5`。CI 使用 OIDC trusted
   publishing，以 npm **`next`** dist-tag **stage** 全部 6 个包并生成 provenance；**stage 不公开任何内容**。
2. 维护者在 npmjs.com 网页核对本次 CI 的 6 条 staged 记录：版本必须全部为 `0.4.2-rc.5`、dist-tag 必须为
   `next`，然后人工批量 approve。approve 即公开且不可撤销；approve 后 `next` 指向本候选，`latest` 仍为
   **0.4.1**。不要批准 rc.1 或 rc.4 的未 approve 历史 staged 记录。
3. approve 完成并核对 dist-tags 后，使用既有 tag 和本文件手动创建 prerelease GitHub Release：

   ```sh
   gh release create v0.4.2-rc.5 --repo yankeguo/dsh-devlead --title v0.4.2-rc.5 \
     --notes-file docs/releases/v0.4.2-rc.5.md --verify-tag --prerelease --latest=false
   ```

4. 最后做三方核对：6 个包的 `@0.4.2-rc.5` 在 npm 可见、`dist-tags.next = 0.4.2-rc.5`、
   `dist-tags.latest = 0.4.1`；GitHub Release 指向 tag `v0.4.2-rc.5` 与同一 commit，
   `isPrerelease=true`、`isLatest=false`、`isDraft=false`。

## English summary

v0.4.2-rc.5 supersedes the staged but never-approved rc.4 without changing its notes or compact-UI feature set.
The shared schema now rejects case-insensitive note-id/path collisions and Windows reserved device names before any
file is written. Host note reads are bounded to 64 KiB of serialized JSON with a Unicode-safe prefix and
`truncated:true`, while stored bodies and browser reads retain the 256 KiB contract; index and body UTF-8 decoding is
fatal. The client hides stale values across workspace-path transitions, keys note watches by primitive id/path/bytes,
and keeps five-second visual polling activity out of the polite live region. Recovery documentation covers malformed
indexes, orphan bodies and stale project entries after board rebuilds. Verification includes 52 files / 1836 tests,
three real DSH rc.5 flows (244/244, 244/244 and 220/220), five killed mutations, package checks and a six-package
`next` dry-run. Nothing becomes public at stage: maintainers must approve only the six new rc.5 records before
creating the prerelease GitHub Release; `latest` stays 0.4.1.
