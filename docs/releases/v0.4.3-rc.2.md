# v0.4.3-rc.2 — `boardPath` 仅支持 lead workspace 相对路径（prerelease，dist-tag `next`）

这是计划中 **0.4.3** 版本的第二个 prerelease 候选，基于 `0.4.3-rc.1` 之后的
`126b079 feat!: require workspace-relative boardPath`。它完整保留 rc.1 的契约收口，并新增一项
**0.x 允许的破坏性配置变更**：非空 `boardPath` 只接受相对 active lead 原始 workspace 根的路径。
既有绝对路径配置必须先迁移，否则升级后会在 Loader 校验或直接构造服务时 fail-fast。

本候选不改 DSH 兼容面：`0.2.2-rc.1` – `0.2.2-rc.5` 与
`engines.dsh: >=0.2.2-rc.1 <0.3.0` 均保持不变。稳定版 `latest` 仍为 **0.4.2**；stage 本身不公开
任何包，也不改变公开 dist-tag。

> 本文件是 GitHub Release 正文。文件提交与 tag/CI stage 不代表已经 approve 或创建 GitHub Release；
> 后续 approve 必须由维护者在 npmjs.com 网页人工完成。tag 一旦推送，**不移动、不删除、不重建**。

## 升级步骤

### 1. 先检查并备份部署配置与看板文件

在加载 rc.2 之前，检查 profile 的 `cordis.patch.yml` 中 loader row `devlead` 的 `config.boardPath`：

- **未配置或 trim 后为空白**：无需改配置，仍派生
  `<lead SessionHeader.cwd>/.dsh/devlead/board.json`。
- **已经使用合法的相对路径**：确认它相对的是 lead Session 创建时的原始 workspace 根，而不是某次
  turn 的 effective/worktree cwd。
- **仍是绝对路径**：必须按下面步骤迁移；rc.2 不会静默忽略它，也不会回退到默认看板。

如需移动文件，先在 `/devlead off` 或停止相关 Host 后备份旧 `board.json` 及其同级 `notes/`
目录。notes 根固定为 `dirname(boardPath)/notes`，移动看板位置时必须一起移动，不能只移动 JSON。

### 2. 把绝对路径改成原始 workspace 内的相对路径

例如 lead 的原始 workspace 根是 `/work/project`，旧配置为：

```yaml
boardPath: /work/project/custom/board.json
```

改为：

```yaml
boardPath: custom/board.json
```

如果旧看板位于 workspace 之外，先把 `board.json` 和同级 `notes/` 一并移入该 workspace，再配置
相对路径。例如把 `/srv/devlead/board.json` 与 `/srv/devlead/notes/` 分别移到
`/work/project/custom/board.json` 与 `/work/project/custom/notes/`，然后使用上面的
`custom/board.json`。workspace 外的看板不再受支持。

### 3. 核对路径安全约束

- 使用 `/` 分隔；不要使用反斜杠、空路径段或 `..` 逃逸。
- 不要配置 POSIX 绝对路径、Windows 盘符路径或 UNC 路径。
- 最终看板路径组件不能是 symlink；父目录链中的 symlink 规则不变。
- 原始 workspace 根必须仍存在且是目录；相对 override 也不会让 Host 重建已删除的 workspace。

绝对路径等非法配置会返回 `BOARD_INVALID`，并带 `/boardPath` validation issue。若升级后看到这个
错误，修正配置再重新加载，不要通过清空配置来掩盖迁移问题。

### 4. approve 后安装精确版本并验证

维护者在 npmjs.com 网页 approve 本次 6 条 staged 记录后，使用精确版本安装；发布后 24 小时内尤其
不要用 `@next`，避免 pnpm `minimumReleaseAge` 回退到 npm 占位版本：

```sh
dsh plugin --profile desktop add @yankeguo/dsh-devlead-bundle@0.4.3-rc.2
```

按正常插件升级流程重新加载 DSH 后，确认看板与 notes 都能从迁移后的路径读取。无需迁移
`board.json` 内容，也无需 `/devlead reset`。rc.1 的工具参数、CAS 与模型路由 breaking 迁移要求仍然
适用，详见 [v0.4.3-rc.1 release notes](v0.4.3-rc.1.md)。

## Breaking：`boardPath` 改为 workspace-relative only

从本候选开始，DevLead 核心配置 `boardPath` 的非空值**只支持相对路径**，相对于唯一 active lead
Session 创建时的原始 workspace 根（`SessionHeader.cwd`）解析，而不是某次 turn 的
effective/worktree cwd。支持的配置示例：

```yaml
- id: devlead
  name: '@yankeguo/dsh-devlead'
  config:
    # 保留部署需要的其他 devlead config 键。
    boardPath: custom/board.json
```

默认值不变：省略或 trim 后为空白（`''`）仍派生
`<lead SessionHeader.cwd>/.dsh/devlead/board.json`。非空 override 通过
`path.resolve(workspaceRoot, boardPath)` 解析，并断言结果仍位于该根内。

旧版本接受绝对路径；本候选会在 Loader 校验或直接构造服务时以 `BOARD_INVALID` 和 `/boardPath`
validation issue **fail-fast**。`SessionHeader.cwd` 缺失、不是绝对路径或目录已不存在时，看板保持
disabled；相对 override 也不能让 Host 重建已删除的 workspace。

### 路径安全规则

- 拒绝 POSIX 绝对路径（如 `/tmp/x`）、Windows 盘符路径（如 `C:\\x`、`C:/x`）与 UNC
  （如 `\\\\server\\share`）。
- 拒绝反斜杠和空路径段；使用 `/` 分隔。
- 拒绝 `..` 逃逸（如 `../x`、`a/../../x`）；解析后必须仍在原始 workspace 根内。
- 看板最终路径组件不能是 symlink；父目录链中的 symlink 规则不变。

## 与 rc.1 的关系及不变量

rc.1 的 per-project revision/CAS、notes metadata-only 工具、4096 码点 assistant 摘要与 8000 码点
wake 载荷上限、lead 主动 interrupt 的 T1 通知、看板持久化移出 git、单 Session archive/restore、
静态模型路由删除等契约均不变。本候选只追加 `boardPath` 配置与路径安全收紧。

- 空白配置的默认派生、原始 workspace 根与 worktree 隔离语义不变。
- notes 根仍固定为已解析 `dirname(boardPath)/notes`；notes schema、正文与 CAS 语义不变。
- board watch、notification、AI 工具参数与浏览器读写契约不变。
- 不需要迁移 `board.json` 内容，也不需要 `/devlead reset`；迁移只涉及部署配置及必要的文件位置调整。
- 不新增 Host API、Remote、`dsh.client.inject` 或高版本-only 依赖。

## English summary

v0.4.3-rc.2 is the second prerelease candidate for the planned 0.4.3 release. It retains every rc.1
contract change and adds one intentional 0.x breaking configuration change: `boardPath` is now
workspace-relative only. Blank keeps the existing `<lead SessionHeader.cwd>/.dsh/devlead/board.json`
default. Absolute POSIX, Windows drive and UNC paths fail Loader validation or direct service construction
with `BOARD_INVALID` and an actionable `/boardPath` issue; there is no silent fallback. Before upgrading,
replace an old absolute value with a path relative to the lead's original workspace (for example,
`/work/project/custom/board.json` becomes `custom/board.json` when that workspace is `/work/project`).
Boards outside that root must be moved into it together with their sibling `notes/` directory. Backslashes,
empty segments and `..` escapes are rejected, and the final component must not be a symlink. Notes
derivation, watch/notification behavior, tool semantics, durable data and DSH compatibility are unchanged;
no board-content migration or `/devlead reset` is needed. Stage publishes nothing: maintainers must approve
only the six new `0.4.3-rc.2` records on `next` before creating the prerelease GitHub Release; `latest`
stays 0.4.2.
