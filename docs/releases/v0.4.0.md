## 变更摘要

### 主线 A：0.3.0 线（自 0.2.6 起新增，additive）

- **Workspace 三寻址**：`workspace` 参数接受 id / 注册目录路径 / 精确 display title（trim 后
  大小写敏感），解析顺序 id → 路径 → title；同 title 命中多个 Workspace 时报
  `DEVLEAD_WORKSPACE_AMBIGUOUS` 并列出候选 id/path，不猜。
- **显式打断 `devlead_prompt_session interrupt`**：经真实 `workspace/session-stop` providers
  停止运行中的 turn 与 subagent/job/schedule 工作、丢弃排队输入，再投递替换 prompt；
  idle/cold 目标是 no-op；被中断的 turn 仍产生 watched 通知（显示 cancelled）。
- **watched 子会话问题路由**：watched 非 lead 子会话的 `ask_user_question` 在问题 UI 运行前被
  `tools/pre-execute` 硬闸门拒绝，格式化为 durable `kind: question` report 转给 active lead；
  question 报告不计入每轮 4 条普通报告预算，转发失败退化为「结束 turn 并写明问题」。
- **排队 inbox 输入可见 / 可撤 / interrupt 保留策略**：`devlead_get_session` 在目标 live 时附带
  `queuedInputs`（稳定 id、boundary、来源、≤240 码点摘要、入队时间）；新工具
  `devlead_retract_input(session, input_id)` 在执行前撤回本 lead 自投的 relay prompt（幂等）；
  `devlead_prompt_session` 新增 `interrupt_inbox`（`clear-all` 默认 / `keep` / `clear-own`），
  以「停止前快照 → stop → 按原 id/boundary 恢复」实现保留，结果新增 `retainedInputs`。
- **审计修复与纪律**：跨 kind 同文 question 去重键修正、inbox 无 source 消息 flush 拒绝处理、
  dispose 等待 outbox 关闭、interrupt 已停后 followup 失败保留 watch 等核心修复；工具描述收窄、
  只读工具声明并发安全、report 指引改为「只用于长任务途中关键节点」。

### 主线 B：In-Turn / Question 消息传递（Phase 1d/1e lanes）

- **三条投递 lane**：`turn-notice`（completed/forked 走 `followup`，保留 400ms 合并）、
  `action-required`（blocked/decision/review/question 走 `steer`，只表示立即调度 flush，最早在
  下一个 pre-step 被 claim）、`background`（progress/fyi 走 `inject`，不请求 driver wake）。
  模型不暴露 `queue|steer|inject` 枚举，runtime 按类别与目标状态选 primitive。
- **answer / correction steering**：`devlead_prompt_session` 的 `intent`
  （`instruction|answer|correction|background`）、`question_id`、`idempotency_key` 与
  `devlead_report` 的 `kind` 共同决定 lane；answer/correction 走 steer 优先道（cold 先 resume；
  `interrupt:true` 仍覆盖为 cancel + followup）。
- **三 lane 读侧与 UI**：`devlead_notifications` / `devlead_get_session` 输出通知行的
  `wakeSuppressedByReportId` / `wakeSuppressionReason`、report 行的 `lane` / `deliveryState`、
  `queuedInputs` 的 `intent` / `questionId` / `wakeRequested` / `deliveryState`，question report
  行附带 fold 派生的 `questionStatus` / `answerStatus` / `answerMessageId` / `answeredAt` /
  `presentedAt`；DevLeadBar 按 lane 着色、显示 question 生命周期后缀，并在
  `DevLeadProjectionReport.repairPending` 时显示 `provisional` /「暂定」。
- **背压与指标**：action-required 16/pair 共享上限（Q1/P3/P4），background 8/lead-turn +
  16/pair 预算降级为 digest-only；correction/background 每 child-turn 4/8 上限返回
  `DEVLEAD_DELIVERY_RATE_LIMITED`；新增 `actionRequiredBatchMs`（0–400ms，默认 0）配置；
  `service.metricsSnapshot()` 暴露低基数计数器（delivery / suppression / guard / answer /
  question）。

### 主线 C：cold-discard durable / repair 收口与 cold supervision 加固

- **OUTBOX spec v3**：`devlead_report_outbox` 升级为 v3、**无 compatible versions**，pending
  report 的 `origin:'live'|'cold'` 必填；旧 v1/v2 domain、无 origin 行与旧 answer-discard 队列
  数据显式丢弃。旧 domain 打不开时 warn 并禁用该 durable domain，不 crash、不写入。
  `answer_discards` 单独保留 **30 天** retention。
- **answerSeq / cold-origin replay**：per-question admission 序号确定 latest answer；cold-observed
  background 经 outbox/persistReport replay 或跨重启只 append receipt + digest-only，绝不 inject；
  `coldQueuedReports` marker 在 settle/drop/dedupe/degrade/watch 变化时清除，live 后也不误投。
- **repair barrier / repairPending**：prompt 在 question policy guard 前等待 drain/repair barrier
  （`REPAIR_BARRIER_TIMEOUT_MS` 30s + `ANSWER_DISCARD_DRAIN_TIMEOUT_MS` 30s，abort 安全退出、
  可重试）；无法证明 survival 时 view 保持 `repairPending`、prompt 以
  `DEVLEAD_SESSION_UNAVAILABLE` fail closed；in-flight drain 窗口对 view/health/prompt 一致可见。
- **multi-batch cold supervision rehydration**：持久语料扫描按 64 读批次、12 次尝试上限 + 30s
  慢速探针；finalize 复核/append 批次各自独立 5s 窗口；`unverifiable` 保留 trusted 快照/游标/
  高水位并计失败，只有可读的不一致（`changed`）才丢弃重扫；corpus 授权绑定真实 service
  provision 身份，admission 入口、drain/repair 之后与真正同步投递前各复核一次，`ctx.set`
  原地替换/移除期间 fail closed；plugin dispose 通过服务生命周期 abort 取消验证读取。

### 主线 D：A 加固（plugin-record 依赖与隐私）

- **plugin-record API 探测 / 降级**：`record-api.ts` 在 init 探测 `appendPluginRecord` /
  `pluginRecordOf`；首次读/写异常转入 `degraded`，失败的那次 append 返回 `false`、read 返回
  `undefined`，只 warn 一次。degraded 时 fold 保持最后有效状态（不写 `failure`、不冻结），
  `/devlead status` 与每个成功命令视图明示 memory-only；writer-only 缺失时健康 reader 仍读回
  既有 durable 状态。该降级只保证插件可加载与状态可见，**不提供 durable 替代存储**。
- **隐私披露**：plugin records 是 canonical session-log events，会进入 session-log ZIP 导出；
  DSH 默认组合、默认 `enabled: true` 的 `session-log-deepseek` 可能把完整 canonical event
  附加到符合条件的官方 DeepSeek 模型请求。README / COMPATIBILITY 记录该上传路径与关闭方式；
  DevLead 不新增上传、不改 DSH 默认配置。
- **升级门禁**：COMPATIBILITY 重写为可执行门禁——核对 record API 声明与语义、deprecated
  reader 清零、逐 rc 临时 typings 编译 + 真实 E2E recipe、record schema/migration 核对。
- **`Session.snapshotEvents()` 迁移完成**：生产调用 **0**（`snapshotEvents()` / `eventAt()` /
  `ownEvents()` 均无调用）。inbox 入队时间、turn source 与 child answer survival 改由有界
  Session projection 承载，cold 侧以 `observeSession()` 读 projection wire value。
- **F 替代方案 no-go 结论**：从 DSH 核心事件派生 mode/watch/reset 的一次性 spike 判定 no-go
  （6 个实质反例），plugin records 的 experimental 依赖仍在；缓解路径是上述 A 加固 + 升级门禁。
  结论与重估条件见 [DESIGN](../DESIGN.md) §4.4.12。

## Breaking changes（相对 0.2.6）

0.4.0 按「正确性 > 兼容性」执行，以下变更是**有意的**、不提供自动迁移：

- **旧 DevLead 状态丢弃**：7 类 `plugin:devlead/*` record 统一为 `version:2`；v1 record 与
  无 `answerSeq` 的旧 answer 显式忽略并丢弃（每进程一次 warning），**不冻结** projection。
  升级后旧 Session 的 DevLead 模式/关注集/digest/answer 状态失效。
- **当前版本损坏仍冻结**：当前 v2 payload 的字段/类型损坏仍设置 `failure` 冻结 projection，
  `/devlead reset` 恢复；坏 reset 不能解冻。
- **projection stateVersion**：`devLead` 7、`devLeadMode` 3、`devLeadWatch` 3；旧缓存行整体
  失效并从 durable log 重新 fold。
- **outbox v3 无兼容**：`OUTBOX_SPEC` v3 无 `compatibleVersions`，`origin` 必填；旧 v1/v2
  outbox、无 origin pending row、旧 answer-discard 队列数据全部丢弃；旧 domain 无法打开时
  禁用该 durable domain。`answer_discards` 30 天 retention 不变。
- **answerSeq 必填**：answer 生命周期事实必须携带 per-question 序号，缺少序号的旧 answer
  record 被忽略（不能作为 answered/presented 证据）。
- **multi-lead 硬门禁**：prompt 侧 foreign / multiple supervisor 直接拒绝
  （`DEVLEAD_FOREIGN_SUPERVISOR` / `DEVLEAD_MULTIPLE_SUPERVISORS`），在任何 watch/resume/
  admission 副作用之前；supervisor 集合不可证明时以 `DEVLEAD_SESSION_UNAVAILABLE` fail closed。
- **question TTL 默认 24h**：`questionTtlMs` 默认 `86400000`，`0` 禁用；只让当前仍 open 的
  question lazy 过期，answered 不 retroactive 过期；过期 answer 返回
  `DEVLEAD_QUESTION_NOT_FOUND`。cold 恢复对 durable、open、未过期 question 每进程最多 replay
  一次，与普通 action report 共用 16/pair 容量。
- **非 answer 幂等改为 durable**：receipt 持久在独立 `devlead_idempotency` v1 domain 的
  `receipts` 表（textHash/delivery/at，7 天 TTL + 启动清理）；同 key 同文本返回原 receipt，
  不同文本冲突。receipt read 的 absent 与 unreadable/corrupt 严格分离，后者以及 composed
  storage 打不开时在 admission 前 fail closed；只有 Host 未组合 storageDomain 时才显式
  warning 后走进程内窗口。
- **回滚同样隐含 reset**：回滚到 `0.3.0-rc.2` 或更旧版本后，旧 fold 对已知类型的 v2 payload
  会 freeze，因此降级也需要 `/devlead reset`；不能宣称「回滚不会因新记录损坏日志」。

## 升级注意事项

- **旧 devlead 状态不迁移**：受影响的 DevLead Session 打开后运行 `/devlead reset`（reset 需要
  live Agent；冷 Session 先 resume/open；`/devlead off` 也可重置冻结折叠），之后重新
  `/devlead on` 并按需重建关注集。不要把它当数据丢失 bug 处理。
- **配置**：`questionTtlMs`（默认 86400000，0 禁用）与 `actionRequiredBatchMs`（0–400ms，
  默认 0）在 loader row `devlead` 的 `config` 覆盖；不要用 deployment 默认值推断运行行为。
- **multi-lead 硬门禁**：Host 级仍只允许一个 active lead；第二个 lead 必须先
  `/devlead off`。archived holder 不阻塞新 enable。
- **引擎/兼容面不变**：`engines.dsh: >=0.2.2-rc.1 <0.3.0` 与全部 `@deepseek-ai/dsh-*`
  peer 范围不变，devDependencies 仍固定 rc.1 做最旧 API 类型检查；本版不声明 DSH 0.4。
- **record API 仍为实验性扩展点**：升级 DSH 前必须按 [COMPATIBILITY](../COMPATIBILITY.md)
  的升级门禁重跑（record API 探测/降级、deprecated reader 清零、逐 rc recipe、真实 E2E）。
- **发布顺序**：6 个包同版本、依赖先发布、bundle 最后；不要只升级部分包。

## 已知限制与 follow-up

- **慢但可读（2–5s）的持久 listing 可能 fail-closed 到 cap/30s probe（可用性加固项）**：持久
  语料 listing 慢但可用时，就绪 barrier 会超 2s 界并返回 unverifiable；入口 verify 即使成功仍
  可能无法 finalize（finalize 复核有独立 5s 预算，需覆盖同一 attempt 内两次 2–5s 读取）。
  后端保持该延迟时，rehydration 会保留 trusted 快照/游标/高水位并计入失败预算，12 次失败后
  进入 sticky cap + 30s 慢速探针，恢复前 prompt 保持 fail closed
  （`DEVLEAD_SESSION_UNAVAILABLE`）。这是安全方向（期间不授权），**不是数据损坏**；原因消除后
  probe 从保留游标 finalize，不重读已扫行。GA 前 follow-up：改用 effective validatedListing
  或在入口 verify 成功后允许 finalize，并补 2s<L<5s 慢 listing 恢复测试。
- **delivery-time supervisor 集合的窄 TOCTOU 窗口（medium，未复现）**：delivery-time
  `SupervisionProof` 只含 `{ bindings, corpusBacked }`，只绑定 corpus service 身份与 rehydrated
  状态；supervisor/watch 冲突只在 gate 时计算一次。admission 内 drain/repair/resume/interrupt
  等 await 期间若 supervisor/watch 集合变化，delivery 复核不重算该集合。因此存在窄、未复现的
  fail-open 窗口（medium）：单 active lead 架构下需要并发 watch 变更才可能触发，本轮未构造出
  单进程可达路径。GA 前建议把 sorted watcher ids 纳入 proof 并在 delivery 前重跑冲突判定。
- **`repairPending` 不是 answer 的 durable 完成证明**：它是 runtime repair 集合的 whole-value
  投影，answer admission 仍以 runtime repair barrier 为准；presented 证据被 evict 后对应
  question 的 stale discard repair 可能长期保持 unknown（per-question），直到新证据出现。
- **round-7 FINAL SAFE 的 4 项 low 代码 nit（已接受，本版不改代码）**：① `proof === undefined`
  时 delivery 复核直接放行（`createSession` 本就不需要 gate proof，当前不可利用，但类型上允许
  未来调用方静默跳过）；② probe reset 清 `rehydrationValidationTimedOut` / `FinalizeBlocked`
  但未清 `rehydrationValidationUnverifiable`；③ `rehydrationScanHighWater = nextIndex` 而非
  `Math.max(old, nextIndex)`；④ scan-entry 的 `changed` 保留快照/游标，而 finalize 复核与
  not-found 两处 `changed` 丢弃。均为低风险加固项，列入 GA 前 follow-up，详见
  [DESIGN §12](../DESIGN.md)。
- **浏览器视觉验收是人工 checklist**：lane 着色、question 状态、`provisional` 标记与状态条
  布局不能只靠单测判断，按 [UI-VERIFICATION](../UI-VERIFICATION.md) 在隔离 profile 里人工
  验收；本版的自动化证据只覆盖 projection/DOM/渲染断言，**不替代**人工验收。
- **`possibleQuestion`（自然语言提问启发式）明确不做**：会把普通文本误判为 question 并改变
  transport（打断/错误 lane），而当前 question gate 已覆盖真实 `ask_user_question` 路径；留作
  backlog，仅在真实模型行为证明需要时重新评估。
- **blocking bridge 只记录指标评估结论**：本版**不实现** blocking bridge / wait tool，只保留
  Phase 3 条件性计划（capability flag、插件内原型；不涉及 DSH 上游改动）；是否值得做由
  `metricsSnapshot()` 的 turn-boundary/延迟指标决定，不作为本版发布承诺。
- **3 条 e2e 检查为 SKIP**：本机 provider 的可用 model list 不含所请求的
  `deepseek-official/deepseek-flash`（无凭据/路由不可用），三条 e2e 各有 3 条正向模型选择
  检查 SKIP；SKIP 未执行、不能算通过。
- **旧数据迁移未做真实 backend smoke**：旧 v1/v2 record/outbox 按设计显式丢弃；本 workspace
  不解析 storage-json/sqlite backend 依赖，未新增依赖。
